==================================================

1. تحليل عنصر LCP الحقيقي

==================================================

شغّل Lighthouse على نسخة الإنتاج وحدد العنصر المسؤول عن LCP في الصفحة الرئيسية.

غالبًا سيكون:

- صورة Hero.

- خلفية Hero.

- عنوان Hero.

- إعلان الصفحة الرئيسية.

اعرض في التقرير النهائي:

- العنصر المسؤول عن LCP.

- حجمه.

- رابط الملف.

- وقت بدء تحميله.

- سبب تأخر اكتشافه.

لا تبدأ بتنفيذ تحسينات عشوائية قبل تحديد عنصر LCP.

==================================================

2. تحسين صورة Hero وصور الإعلانات

==================================================

نفّذ نظام صور متجاوب بالكامل.

لصورة Hero أو الإعلان الرئيسي:

- أنشئ نسخة هاتف بعرض مناسب بين 480 و768 بكسل.

- أنشئ نسخة Desktop منفصلة.

- حوّل الصور إلى AVIF مع WebP كبديل.

- لا ترسل صورة Desktop الكبيرة إلى الهاتف.

- اضغط الصور مع الحفاظ على جودة بصرية ممتازة.

- اجعل حجم صورة Hero للهاتف أقل من 150KB قدر الإمكان.

- اجعل صور البطاقات أقل من 80KB قدر الإمكان.

استخدم:
<picture>
<source type="image/avif" ...>
<source type="image/webp" ...>
<img ...>
</picture>

مع:

- srcset

- sizes

- width

- height

مثال منطقي:

sizes="(max-width: 768px) 100vw, 50vw"

صورة LCP يجب أن تستخدم:

fetchpriority="high"

loading="eager"

decoding="async"

يمنع استخدام:

loading="lazy"

على صورة LCP أو صورة Hero الرئيسية.

أضف preload لصورة الهاتف المستخدمة كعنصر LCP داخل head:
<link

  rel="preload"

  as="image"

  href="..."

  imagesrcset="..."

  imagesizes="..."

  fetchpriority="high"

/>

تأكد أن preload يطابق بالضبط الصورة التي يعرضها المتصفح، ولا تقم بتحميل نسختين من الصورة.

==================================================

3. الصور الموجودة أسفل الجزء المرئي

==================================================

كل صورة ليست ظاهرة مباشرة عند دخول الصفحة يجب أن تستخدم:

loading="lazy"

decoding="async"

ويجب تحديد:

width

height

لمنع CLS.

لا تستخدم Lazy Loading لما يلي:

- الشعار الظاهر أعلى الصفحة.

- صورة Hero.

- الإعلان الموجود فوق Fold.

- أي صورة مسؤولة عن LCP.

استخدم IntersectionObserver للمكونات الثقيلة أسفل الصفحة عند الحاجة.

==================================================

4. منع تحميل الصور الأصلية الضخمة

==================================================

راجع نظام رفع الصور من لوحة الإدارة.

عند رفع صورة إعلان أو صورة محتوى:

- لا تعتمد على الملف الأصلي مباشرة في الموقع.

- أنشئ نسخًا محسنة تلقائيًا.

- mobile AVIF

- mobile WebP

- desktop AVIF

- desktop WebP

- thumbnail

احفظ معلومات كل نسخة في قاعدة البيانات أو التخزين.

يجب أن تعرض الواجهة النسخة المناسبة لحجم الشاشة.

ضع حدًا لحجم الملف الأصلي، مع رسالة عربية واضحة للمشرف.

==================================================

5. التخزين المؤقت Cache-Control

==================================================

اضبط رؤوس التخزين المؤقت للملفات ذات الاسم المحتوي على hash:

Cache-Control: public, max-age=31536000, immutable

يشمل:

- JavaScript bundles

- CSS bundles

- AVIF

- WebP

- SVG

- WOFF2

- الصور الثابتة

لملف HTML:

Cache-Control: no-cache

أو سياسة قصيرة تسمح دائمًا بالتحقق من النسخة الجديدة.

للمحتوى الديناميكي والصور التي قد تتغير دون hash:

Cache-Control: public, max-age=3600, stale-while-revalidate=86400

تأكد أن تغيير الملف يؤدي إلى اسم جديد يحتوي على hash حتى لا تظهر نسخة قديمة.

تحقق من رؤوس الملفات على النطاق الحقيقي وليس localhost فقط.

==================================================

6. تقليل JavaScript غير المستخدم

==================================================

طبّق Route-Based Code Splitting.

لا تحمل صفحات المنصة كلها عند فتح الصفحة الرئيسية.

استخدم React.lazy وSuspense للصفحات التالية:

- لوحة الطالب.

- لوحة الإدارة.

- Study Room.

- Study Schedule.

- صفحة الامتحان.

- محرر الامتحانات.

- إدارة الدوسيات.

- إدارة أوراق العمل.

- إدارة الإعلانات.

- صفحات الإحصائيات.

- أي مكتبة رسومات أو جداول ثقيلة.

مثال:

const AdminDashboard = lazy(() => import("./pages/admin/AdminDashboard"));

لا تستورد لوحة الإدارة داخل الـ bundle الرئيسي.

راجع المكتبات الثقيلة، خصوصًا:

- chart libraries

- rich text editors

- PDF viewers

- date libraries

- animation libraries

- icon libraries

لا تحملها على الصفحة الرئيسية إن لم تكن مستخدمة.

استورد الأيقونات بشكل منفصل ولا تستورد مكتبة أيقونات كاملة.

استخدم tree shaking.

أزل:

- imports غير مستخدمة.

- مكونات قديمة.

- مكتبات مكررة.

- polyfills غير ضرورية.

- debug packages من production.

أنشئ Bundle Analyzer واعرض أكبر 15 ملفًا في التقرير.

الهدف:

تقليل JavaScript المستخدم في التحميل الأولي للهاتف بمقدار 307KB على الأقل إن أمكن.

==================================================

7. إزالة الموارد التي تمنع الرسم

==================================================

حدد ملفات CSS والخطوط والسكربتات التي تمنع First Paint.

نفّذ:

- Inline للـ Critical CSS الضروري أعلى الصفحة إن كان ذلك مناسبًا.

- تحميل CSS غير الضروري بشكل غير حاجب.

- حذف CSS غير المستخدم.

- minify كامل للـ CSS والـ JS.

- تأجيل السكربتات غير الضرورية باستخدام defer.

- عدم تحميل أي JavaScript تابع لجهة خارجية قبل الحاجة.

لا تحمّل:

- Analytics.

- Chat widgets.

- أدوات إعلانات.

- Heatmaps.

- أي tracking غير أساسي.

قبل ظهور المحتوى الرئيسي.

يمكن تأخيرها حتى:

- بعد load.

- بعد أول تفاعل.

- أو باستخدام requestIdleCallback.

==================================================

8. تحسين الخطوط العربية

==================================================

راجع الخطوط المستخدمة.

استخدم WOFF2 فقط.

لا تحمّل أوزانًا كثيرة غير مستخدمة.

يفضل الاكتفاء مثلًا بـ:

- 400

- 600

- 700

استخدم:

font-display: swap

أضف preload لخط واحد أساسي فقط إذا كان مستخدمًا مباشرة في Hero.

لا تعمل preload لجميع الأوزان.

استخدم Unicode Subsetting للخط العربي إن كان متاحًا.

أضف fallback مناسبًا حتى يظهر النص فورًا دون شاشة فارغة.

تأكد أن الخطوط يتم تقديمها مع Cache-Control طويل.

==================================================

9. تقليل Main Thread والعمل الطويل

==================================================

حدد Long Tasks الأكبر من 50ms.

راجع:

- عمليات parsing كبيرة.

- loops أثناء render.

- حسابات متكررة.

- useEffect غير الضرورية.

- إعادة render واسعة.

- context providers التي تعيد رسم التطبيق كاملًا.

- animations تعتمد على JavaScript.

- عمليات DOM ثقيلة.

طبّق عند الحاجة:

- React.memo

- useMemo

- useCallback

لكن لا تستخدمها عشوائيًا.

انقل العمليات الثقيلة غير الضرورية بعيدًا عن التحميل الأول.

لا تقم بجلب بيانات كل أقسام الموقع مرة واحدة.

==================================================

10. تحسين طلبات API في الصفحة الرئيسية

==================================================

لا تجعل الصفحة الرئيسية تنتظر عدة API calls متسلسلة.

اجمع بيانات الصفحة الرئيسية في endpoint واحد خفيف، مثل:

GET /api/public/homepage

يعيد فقط البيانات الضرورية لعرض Above the Fold.

لا تعِد بيانات كبيرة أو حقولًا غير مستخدمة.

نفّذ الطلبات المستقلة بالتوازي بدل التسلسل.

أضف caching مناسب للبيانات العامة.

لا تجعل ظهور Hero ينتظر:

- إحصائيات.

- أقسام أسفل الصفحة.

- بيانات المستخدم.

- بيانات لوحة الإدارة.

- بيانات الامتحانات كاملة.

اعرض المحتوى الثابت الأساسي فورًا.

==================================================

11. Critical Request Chains

==================================================

افحص Network Dependency Tree.

قلل سلاسل التحميل المتتابعة مثل:

HTML

→ CSS

→ font CSS

→ font

→ JavaScript

→ API

→ Hero image

المطلوب:

- اكتشاف صورة LCP من HTML مباشرة.

- عدم اكتشافها بعد تشغيل JavaScript.

- عدم تحميلها من CSS background-image إن كان ذلك يؤخر اكتشافها.

- يفضل استخدام عنصر img أو picture لصورة Hero.

- preload للخط أو الصورة الضرورية فقط.

- تقليل عدد الاتصالات الحرجة.

==================================================

12. عدم استخدام Background Image للـ LCP

==================================================

إذا كانت صورة Hero أو الإعلان مستخدمة عبر:

background-image: url(...)

وتبيّن أنها عنصر LCP، حوّلها إلى:
<picture>
<img>
</picture>

مع الحفاظ على التصميم باستخدام:

object-fit: cover

position: absolute

واجعل النص فوقها كما هو.

الهدف هو أن يكتشف المتصفح الصورة مباشرة من HTML.

13. تحسين استجابة الخادم

==================================================

افحص TTFB من النطاق الحقيقي.

إذا كان مرتفعًا:

- امنع الاستعلامات غير الضرورية في الصفحة الرئيسية.

- أضف caching للبيانات العامة.

- راجع cold start.

- راجع اتصال قاعدة البيانات.

- لا تنفذ migrations عند كل تشغيل.

- لا تنشئ اتصالات قاعدة بيانات جديدة لكل طلب.

- استخدم connection pooling.

- لا تجعل auth check يمنع عرض الصفحة العامة.

الهدف:

TTFB أقل من 800ms على الهاتف قدر الإمكان.
